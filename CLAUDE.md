## Roclec native workflow

This project uses Roclec profile 3 for immutable capability contracts, explicit changes, component releases and candidate-bound evidence. Read `.roclec/workflow.md`, `.roclec/model.md`, the profile and applicable agreed consumer references. Use `./.roclec/run --json COMMAND ...`; this launcher supplies the configured project root, including in a linked code repo.

Inspect explicit IDs with exactly one canonical selector: `inspect --change CHG-ID`, `inspect --capability CAP-ID`, `inspect --fut FUT-ID`, or `inspect --release VERSION --component NAME`. Do not select by branch guesses or the newest directory. Mutations require explicit scope/component. Keep templates, principles, architecture and product/design decisions consumer-owned. Use approval and integration/publication operations, not editable done states. Current.json is the integrated vector; release.json alone owns release membership; views are generated. Do not edit immutable snapshots, approved revisions, runs, decisions, preparations or publications.

When the user asks to start or resume a Roclec change, load `roclec-coordinator` as the entry point. Use it to choose and execute the appropriate native skills through authorized integration. The coordinator delegates bounded stages to the installed subagent roles `roclec-specifier`, `roclec-implementer` and `roclec-reviewer` when the host supports them, and runs them in sequence itself otherwise. Roles follow their definitions, return Roclec records and open questions, and never approve, integrate or publish. The declared flow in `.roclec/flow.toml` governs delegation and human stops: stop at every checkpoint and `ai = false` stage, and record decisions with the person's own `--criteria` evaluation. Answer status-only requests with read-only inspection. Approval, release membership, runs and reviews must all match the current intent revision; stale evidence remains history. A structured workflow gate is evidence of a blocker, while invalid invocation, IO failure or malformed output is a technical failure. Do not repeat a failed command without an authorized precondition change. A check pass is structural evidence; a run pass does not substitute for coverage, adopted review or actual visual approval. Record decisions only with real provenance. Do not create/push tags, deploy or send messages merely to satisfy a gate. Optional spec-kit aliases use these same native instructions and have no independent authority.
